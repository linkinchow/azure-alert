# 升级到新版本

升级就是**用最新模板再部署一次**。部署是增量的：已有资源就地更新，不会重建，也不会丢失 Pull 模块的去重记录，升级过程中告警照常工作。

## 升级前确认

| 项目 | 说明 |
|---|---|
| 订阅、资源组名称、前缀 | **必须和第一次部署完全一样**，否则会再部署出一整套，同一事件收到两张卡片 |
| 飞书 webhook | 默认 webhook 和"按分类路由"是加密参数，门户不会记住，要重新填写 |
| 模块 | 勾选所有正在用的模块（已部署的 + 想新加的）。没勾的模块不会被删除，但也不会升级 |
| 权限 | 和第一次部署相同：订阅上的 Owner，或 Contributor + User Access Administrator（要创建角色分配） |

查看第一次部署时用的参数（订阅、资源组、前缀、模块等），可以用：

```bash
python scripts/export-params.py                 # 列出这个订阅里的 azure-alert 部署记录
python scripts/export-params.py <部署名称>       # 显示参数（webhook 是加密的，显示为占位符）
```

## 方式一：门户

1. 打开 README 顶部的 **Deploy to Azure** 按钮（总是最新版本）。
2. 订阅、区域、**资源组名称、前缀**填得和第一次一样。
3. "告警模块"里勾选所有需要的模块。
4. "飞书通知"一步：
   - 重新填写默认 webhook；
   - "按分类路由"填回原来的内容。如果原来所有告警都发到一个群，保留预填的空模板即可；
   - "重复告警降频"保持"开启（推荐）"。
5. 其他参数（订阅范围、M4 区域和阈值等）按第一次填写，创建。

## 方式二：命令行

```bash
git pull                                                          # 拿到最新代码
python scripts/export-params.py <部署名称> > upgrade.local.json   # 从上次的部署记录导出参数
# 编辑 upgrade.local.json：把 defaultWebhook / webhooks 的占位符换成真实地址
az deployment sub create -l <区域> -n azure-alert -f main.bicep -p @upgrade.local.json
```

`*.local.json` 不会被提交到 git（含 webhook，不要外传）。

## 升级后检查

1. 部署状态是"成功"。
2. 中心资源组里能看到：
   - Logic App `<前缀>-router`（已更新）；
   - 新的存储账户 `<前缀>st…`（重复告警降频用），"网络"里公网访问是"已禁用"；
   - 每个推送订阅里多一条活动日志告警 `<前缀>-m3-resource-health-recovery`（勾了 M3 时）。
3. 之后的第一张卡片照常到达飞书群。如果有正在反复出现的告警，升级后它还会再发 2 次，然后进入每天最多一次。

## 升级后的变化（按版本）

| 日期 | 变化 | 对已部署客户的影响 |
|---|---|---|
| 2026-11-14 | **重复告警降频**（M3 / M7）：同一告警 24 小时内前 2 次照发，之后每天、每周、每月最多一张；**M3 "已恢复"卡片**。见 [repeat-suppression.md](repeat-suppression.md) | 新增一个不开放公网的存储账户、一个角色分配、每个推送订阅一条 M3 恢复规则。不想要可以在向导里关闭，或参数 `repeatSuppression = { "enabled": false }` |
| 2026-11-10 | M3 / M7 卡片的"时间"改为事件实际发生的时间（原来是告警触发时间，晚 5～30 分钟） | 无需操作 |
| 2026-11-10 | 新增 **M9 Key Vault 到期提醒**（证书、机密、密钥），见 [keyvault-expiry.md](keyvault-expiry.md) | 默认不选。要用的话升级时勾选并选择 Key Vault，或升级后用脚本接入 |
| 2026-11-10 | M6 前提脚本：不再修改 AKS 节点池等平台托管的资源；可用性集改为在集合上开启 | 只影响脚本，无需重新部署 |
| 2026-11-09 | M7 告警规则修复：部分订阅部署时报 `UnsupportedCondition` | 之前部署 M7 失败的，升级即可 |

## 回退

- 关闭重复告警降频：再部署一次，向导里选"关闭"，或参数 `repeatSuppression = { "enabled": false }`。关闭后所有告警恢复为每次都发，M3 不再发"已恢复"。存储账户和 `<前缀>-m3-resource-health-recovery` 规则不会自动删除，不需要的话手动删除。
- 其他改动都是修复，不建议回退。确实需要时，用旧版本的代码（`git checkout <提交>`）按命令行方式再部署一次。
