# 重复告警降频

同一个资源的同一个告警反复出现时（例如健康探测配置有问题的 Front Door，每小时都报一次"Unavailable Backends"），不再每次都发卡片，而是逐步降低提醒频率，避免真正重要的消息被淹没。

默认对 **M3 资源健康**和 **M7 操作失败**生效，部署时默认开启。

## 规则

"同一个告警" = 同一个资源 + 同一个分类 + 同一个标题。同一个 Front Door 的"后端不可用"和"自定义域证书过期"是两个不同的告警，分别计数。

| 阶段 | 发送规则 |
|---|---|
| 新告警 | 立即发送；24 小时内的前 2 次都照发 |
| 第 3 次起，前 7 天 | 每天最多一张 |
| 之后 4 周 | 每周最多一张 |
| 再之后 | 每月最多一张 |
| 连续 3 天没有再出现 | 重新计数，下次出现当作新告警 |

### 每次告警怎么判断

每个告警在状态表里记录：首次出现时间、最近出现时间、最近发送时间、累计次数、上次发送后跳过的次数。每来一次，按顺序判断：

1. 没有记录，或者距**最近出现时间**超过 3 天：当作新告警，计数从 1 开始，立即发送。
2. 累计次数 ≤ 2，并且距**首次出现**不超过 24 小时：照常发送；第 2 张带提示。
3. 否则按距**首次出现**多久定间隔：7 天内 1 天；之后 4 周内 7 天；再之后 30 天。
4. 距**最近发送时间**已满这个间隔：发一张【重复】汇总；没满：不发，跳过次数加 1。

需要注意：

- **不是定时发送**：汇总卡在"间隔已满之后，告警**再次出现**"时才发。问题不再出现就不会再发，所以每天那张的时间会逐渐往后漂。
- 每天 / 每周 / 每月的阶段按**首次出现**算；"安静 3 天"按**最近一次出现**算，被跳过的那几次也算出现。
- 安静不到 3 天又出现：不重新计数，继续当前阶段；如果距上次发送已满一个间隔，直接发【重复】汇总。
- 第 2 张卡片会提示：**提示**：同一告警 24 小时内已出现 2 次，之后改为每天最多提醒一次。
- 【重复】卡片的标题前加"【重复】"，正文第一行写明这段时间的情况，例如：

  ```
  严重｜资源健康｜【重复】afd-web：Unavailable Backends
  **重复提醒**：上次提醒（11-20 09:15）以来又发生 23 次；首次出现 11-19 08:40，累计 31 次。同一告警之后每天最多提醒一次。
  ```

例子：一个资源从周一 10:00 起每小时报一次。

| 时间 | 卡片 |
|---|---|
| 周一 10:00（第 1 次） | 照发 |
| 周一 11:00（第 2 次） | 照发，带提示 |
| 周一 12:00 起 | 不发 |
| 周二约 11:00（距上次发送满 24 小时后的第一次） | 【重复】又发生约 24 次 |
| 之后到第 7 天 | 每天 1 张 |
| 第 8 天起 | 每周 1 张 |
| 第 36 天起 | 每月 1 张 |
| 连续 3 天不再出现后又出现 | 当作新告警，从第 1 次开始 |

其他说明：

- 指标告警（M4）不需要降频：Azure 在告警持续期间不会重复触发。
- Pull 模块（M1、M2、M5、M6、M8）本来就按事件去重，同一个事件只发一次，默认不降频。
- "告警系统自检"永远不降频。

## M3 不发"已恢复"

M3 只通知不可用 / 降级，不发"已恢复"卡片。

资源健康的"恢复"（变回 Available）不一定代表问题解决了。实测（2026-11）：一个没有流量、后端健康探测一直 0% 成功的 Front Door，资源健康状态每 10～40 分钟在"不可用"和"可用"之间来回切换，恢复事件里的标题、详情、原因都是 Unknown。后端探测、负载均衡探测等依赖客户配置的健康检查都可能这样，没有通用的办法分辨真假恢复，所以不发。需要确认是否恢复，点卡片上的"在 Azure 门户中查看"看资源健康的当前状态。

2026-11-14 的版本曾经发"已恢复"，并在每个推送订阅建了规则 `<前缀>-m3-resource-health-recovery`。之后的版本不再建这条规则，Router 也会丢弃它的事件；已经建出来的可以删除：

```bash
python scripts/remove-module.py --prefix <前缀> --resource-group <中心资源组> --module m3-recovery           # 先列出
python scripts/remove-module.py --prefix <前缀> --resource-group <中心资源组> --module m3-recovery --apply   # 删除
```

## 状态保存在哪里

在中心资源组里新建一个存储账户（名称是 `<前缀去掉连字符的前 9 位>st<随机串>`），里面一张表 `alertstate`，每个告警一行，记录首次出现、最近出现、最近发送的时间和次数。

- **网络**：公网访问"已禁用"，也**不**开"允许受信任的 Microsoft 服务"例外，只用一条**资源实例规则**放行 Router（`Microsoft.Logic/workflows` `<前缀>-router`）这一个资源，其他任何资源和 IP 都连不上（已实测：去掉这条规则后 Router 被拒绝，403）。
- **认证**：禁用访问密钥，只能用 Entra ID 认证。Router 用自己的**系统分配托管身份**读写（资源实例规则按资源的系统分配身份识别），角色是 Storage Table Data Contributor，只授予在这个存储账户上。Router 的其他操作仍用原来的用户分配身份。
- 费用每月不到 1 美元。
- **读写失败时照常发送**，宁可多发，不会漏发。

因为没有公网访问，在自己电脑上用 Azure CLI 或门户的"存储浏览器"看不到表里的数据，这是正常的。需要查看或清除时，见文末。

## 配置

部署向导"飞书通知"一步里有"重复告警降频"开关，默认开启。

命令行部署用参数 `repeatSuppression`，只需要写要改的字段，其余用默认值：

```json
"repeatSuppression": { "value": { "enabled": true } }
```

| 字段 | 默认值 | 说明 |
|---|---|---|
| `enabled` | `true` | `false` 关闭降频，也不会建存储账户 |
| `categories` | `["ResourceHealth", "ActivityFailure"]` | 生效的分类，可以写完整分类名或前缀（点号前的部分） |
| `burstCount` | `2` | 新告警在 `burstWindowHours` 内照发几次 |
| `burstWindowHours` | `24` | 见上 |
| `dailyDays` | `7` | 每天一次持续几天 |
| `weeklyWeeks` | `4` | 之后每周一次持续几周，再之后每月一次 |
| `quietDays` | `3` | 连续多少天没再出现就重新计数 |

关闭降频后，已经建出来的存储账户不会自动删除（部署是增量的），不需要的话可以手动删除。

## 查看和清除状态

表里的数据只有 Router 能读写，一般不需要手动处理：问题消失 3 天后会自动重新计数。

确实需要全部清零时（例如修好了一批问题，想让下次出现马上提醒），不要为此打开存储账户的网络访问，用 ARM 管理面删除整张表，再重新部署一次（重新部署会建回空表）：

```bash
az rest --method delete --url "https://management.azure.com/subscriptions/<订阅 ID>/resourceGroups/rg-azure-alert/providers/Microsoft.Storage/storageAccounts/<存储账户名>/tableServices/default/tables/alertstate?api-version=2024-01-01"
```

删除到重新部署之间，所有告警照常发送，不会漏。
